# More request-path waste - 2026-10-21

PR verification update: the Bun cursor-stack candidate below was later removed because it exceeded
the existing edge bundle-size budget without an established HTTP throughput gain. The final PR
keeps the native array stack on every runtime, immediate cleanup on poisoning rejection, and the
query/validation changes below. The dated candidate measurements remain unchanged.

Three additional changes reduce prototype traversal work, encoded-query materialization, and
generic validation allocations. The strongest Bun improvements occur on nested JSON and encoded
queries. Node's improvements are smaller. These measurements do not establish a consistent win
over Elysia or Fastify across applications.

## Bun JSON traversal

A CPU profile of 110,000 actual generic large POSTs attributed about 32% of Nifra's sampled self
time to the prototype guard's sweep and another 11% to native `Array.pop`. The security walk is
necessary; its stack bookkeeping was the target. The profile includes startup and warmup and
is attribution, not a throughput result.

The retained implementation chooses its stack once at module load. Bun gets a small JavaScript
cursor stack whose push/pop can inline. Node and Deno retain their native array stack. Both use
the same security walk and inspect the same keys and nested values. Successful Bun walks clear
their backing storage; rejection clears pending references immediately. No per-request stack or
new recursive walk is introduced.

Eight-round helper A/B, reused parsed clean values, ordinary medians:

| Shape | Bun before / after ns | Node before / after ns |
| --- | ---: | ---: |
| 88 records | 1,253 / 1,131 | 1,458 / 1,461 |
| 560 records | 7,588 / 6,536 | 8,786 / 8,856 |
| Small nested tree | 95.5 / 67.9 | 96.3 / 96.4 |

This is about 10-14% less guard time on Bun's record arrays and 29% on the small nested tree.
Scalar, flat, wide, and scalar-array controls are included in the evidence; Node stays approximately
neutral. A shared manual cursor and a per-iteration runtime branch both regressed Node cases and
were rejected. A direct-root loop also regressed Bun cases. One shared policy walk with a
once-selected stack avoids those regressions and duplicated security logic.

## Encoded query materialization

The encoded-query fallback now uses `URLSearchParams.forEach` instead of its iterator's pair
arrays. The parser, key interning, null-prototype output, duplicate-key promotion, and ordering
remain the same. The plain-query scanner is unchanged.

| Query shape | Bun before / after ns | Node before / after ns |
| --- | ---: | ---: |
| Two fields, encoded value | 354 / 295 | 411 / 390 |
| Plus signs, empty and bare values | 454 / 340 | 484 / 439 |
| Repeated encoded key | 566 / 460 | 850 / 818 |
| Malformed escapes and sensitive keys | 714 / 581 | 2,830 / 2,798 |
| 16 encoded fields | 3,045 / 2,425 | 3,737 / 3,645 |

Bun's encoded fallback takes 17-25% less time in these phase measurements; Node's reduction is 1-9%.
Plain-query control medians are approximately unchanged. These phase timings exclude routing,
networking, and Request construction. Bun producer time fell about 7% for the closed encoded GET
and 14% for the generic encoded GET. Other producer controls vary, including
a +3% time difference on the closed plain GET; a microbenchmark does not establish universal
end-to-end ordering.

## Generic validation callbacks

Successful generic validation assigns the validated value directly. Its recovery callback is now
created only when a recovery hook needs it. Two stateless body-parser callbacks are shared rather
than constructed on each body validation. Recovery, synchronous/asynchronous validation, and
error propagation retain their existing contracts.

Four balanced V8 allocation-sampling windows of 30,000 requests, including objects collected by
minor and major GC, produced these ordinary medians:

| Generic workload | Before sampled JS B/request | After | Difference |
| --- | ---: | ---: | ---: |
| GET | 6,570 | 6,469 | -101 |
| POST 10.4 KiB | 35,566 | 35,395 | -171 |
| POST 66.3 KiB | 177,640 | 177,547 | -94 |

The large-body difference is small relative to sampling variation. These are sampled cumulative JS
allocations, not exact counts, RSS, native allocation totals, or retained heap. They apply to the
generic path; this does not claim a corresponding improvement in the existing fused real-world
POST benchmark.

## HTTP checks against the saved baseline

The final Bun A/B uses equally bundled before/after factories, the same diagnostic server entry,
five untimed warmup batches per workload and peer, six rotating/reversing rounds, and 50
connections. Per measured window: 50,000 GETs, 15,000 small POSTs, and 5,000 large POSTs. Response
and rejection probes precede load; every measured request must complete with 200.

| Bun generic workload | Before req/s | After req/s | Difference |
| --- | ---: | ---: | ---: |
| GET | 105,815 | 107,730 | +1.8% |
| POST 10.4 KiB | 47,211 | 46,992 | -0.5% |
| POST 66.3 KiB | 11,835 | 12,161 | +2.8% |

Large-POST p99 was 8.31 / 8.13 ms in those selected median-throughput samples. The same run's
Elysia large POST was 13,110 req/s, so Nifra still trails it by about 7.2%. Earlier native-candidate
versus bundled-baseline runs suggested larger gains; packaging differs there, so the table uses
the matched result. Small differences remain uncertain on this workstation.

Node's initial timing run varied substantially and could not resolve the GET result. The final
isolated GET repeat uses eight balanced 500,000-request windows after 500,000 warmup requests per
variant. Median throughput was 94,468 -> 97,297 req/s (+3.0%); server CPU was 10.90 -> 10.59
us/request (-2.9%). This is a local result, not a consistency guarantee or a new peer ranking.
The initial POST timing data remains in the evidence without a speedup claim.

## Correctness and remaining scope

2,848 Bun tests, 76 real Node tests, and four profiling/compiled-plan tests pass. `nifra check
--json`, the core performance gate, scoped Biome, and `git diff --check` pass. A deterministic
500-shape differential test covers all three poisoning policies against a reference walk,
alternating broad, narrow, poisoned, and clean trees. Dedicated Node tests cover pending-work
cleanup and 20,000-level nesting. Existing caps, Unicode-escaped poison names, body replay,
streaming, query duplicates, malformed escapes, and recovery tests remain in the passing suites.

The profile also attributes significant time to validation of the benchmark's hand-written
Standard Schema. That includes application-validator work, so changing the benchmark's validator
would not count as a framework optimization. A separate first-party compiled-schema workload is
a useful next attribution case. Async lifecycle continuations and response materialization remain
other candidates; they need isolated measurements before adding complexity or changing contracts.

Bun's heap profiler is a retained snapshot, not an allocation sampler. No Bun bytes/request
allocation claim is inferred from it. The existing memory benchmark remains a separate dated
Node process-footprint capture.

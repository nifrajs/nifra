# HTTP profiling - 2026-10-21

The current results do not establish a consistent win over Fastify or Elysia. They do identify
two concrete costs to target: generic GET dispatch and POST allocation churn. The largest measured
throughput deficit in the bounded generic matrix was 6.4%, on Bun versus Elysia's large POST.

## The old worst-case fixture was eligible for fusion

One derive, one before hook, and one after hook qualify for the current closed-shape lifecycle
fusion. Dynamic path parameters, query validation, and dynamic headers do not exclude it.
The real-world fixture also qualifies for derive-before/body-derive-before fusion.

`BENCH_GENERIC=1` now adds a second no-op before hook to every peer. Nifra consequently runs the
generic lifecycle program. A test checks the actual compiled plans for both GET and POST, so a
future optimizer cannot silently invalidate this comparison. Default fixture behavior is preserved.

## Generic HTTP throughput

Six interleaved count-bounded rounds, 50 connections, on this macOS ARM64 workstation. Bun 1.4.3,
Node 26.12.0, Deno 2.9.7, Fastify 5.12.7, Elysia 1.4.30, and its Node adapter 1.4.5. Nifra uses built
workspace artifacts. Each workload has successful response/header probes and validation/rejection
probes before load. The table reports ratios of the selected median-throughput samples, not a
statistical confidence interval or a worst observed latency. Positive means Nifra is faster.

| Runtime / peer | GET | POST 10.4 KiB | POST 66.3 KiB |
| --- | ---: | ---: | ---: |
| Bun / Elysia | -5.5% | -6.1% | -6.4% |
| Node / Fastify | -3.5% | +4.3% | +8.1% |
| Node / Elysia | +33.5% | +24.5% | +5.5% |
| Deno / Elysia | +15.1% | +14.7% | +5.4% |

The matrix used 30,000 GET, 9,000 small POST, and 3,000 large POST requests per round. The separate
Node CPU run used 20,000 requests per round and forced collections outside the CPU window. It put
generic GET 7.2% behind Fastify. The two protocols agree on the direction but differ on magnitude;
the plausible local signal is a roughly 4-7% GET deficit, requiring a quieter repeat to tighten it.

This is a valid-request stress matrix. It excludes asynchronous hooks, response-contract enforcement,
large streaming/chunked uploads, high-cardinality route churn, and sustained error traffic. It does
not define an absolute worst case across all framework features or application workloads.

## Real-world Node CPU and allocations

CPU medians use six balanced rounds of 100,000 requests each, including user and system CPU across
the server process. Allocation estimates use three separate 100,000-request windows with V8 heap
sampling at 16 KiB, retaining samples for objects collected by minor and major GC.

| Real-world workload / metric | Nifra | Fastify | Elysia |
| --- | ---: | ---: | ---: |
| GET CPU us/request | 19.11 | 19.52 | 30.16 |
| POST CPU us/request | 16.79 | 16.06 | 29.39 |
| GET sampled JS bytes/request | 10,395 | 10,542 | 19,127 |
| POST sampled JS bytes/request | 10,708 | 9,556 | 24,762 |

GET allocation volume is essentially level with Fastify. POST allocates about 1,152 additional JS
bytes per request, or 12.1%, while using about 4.5% more total CPU. Same-round throughput ratios put
GET 2.5% ahead of Fastify, winning five of six windows; POST was 3.1% behind, winning one of six.
These are local observations, rather than a reproduction of a particular published benchmark run.

The POST allocation trace attributes roughly 850 bytes/request to `readBoundedJsonSource`, with
additional allocations in the transport source and lifecycle continuations. The trace points to
promise/closure state around body reading, validation, and continuation delivery as a useful target.
An allocation stack identifies where allocations were attributed; it does not prove all of them
are unnecessary or isolate a function's causal CPU cost.

The forced-generic allocation sample has the same pattern:

| Generic workload / sampled JS bytes per request | Nifra | Fastify | Elysia |
| --- | ---: | ---: | ---: |
| GET | 6,942 | 7,422 | 13,533 |
| POST 10.4 KiB | 36,023 | 32,097 | 52,844 |
| POST 66.3 KiB | 177,675 | 158,128 | 208,731 |

These generic allocation results use one 20,000-request sample per cell and need replication.
They suggest that Nifra's POST allocation excess persists with larger bodies. They do not show a
GET allocation excess that would explain its generic CPU deficit.

## Bun microprofiling

The in-process GET microbenchmark removes networking and Request construction, reuses one bodyless
Request, and measures response production without draining bodies. Eight balanced rounds of
100,000 requests produced these medians:

| Shape | Nifra ns/request | Elysia ns/request |
| --- | ---: | ---: |
| Closed lifecycle shape | 1,027 | 1,022 |
| Generic lifecycle shape | 1,046 | 1,023 |

Small differences varied between local runs. These are producer costs, not HTTP latency. They
confirm that a small generic-path difference remains when networking is removed, without proving
a stable 2% ordering.

Separate Bun CPU profiles of four million generic GETs show Nifra spending self-time in
`routeAndRun` (~10%), `runHooksSync` (~8%), `queryObjectOf` (~8%), `setQueryValue` (~6%), and
`buildParams` (~3%). Response JSON creation and header operations account for much of the rest.
Node's generic profile likewise points to routing, parameter/query materialization, and result
classification, spread across several functions rather than one dominant avoidable frame.

## Memory footprint is different from allocation churn

During the real-world GET windows, median RSS was about 71 MiB for Nifra, 90 MiB for Fastify, and
94 MiB for Elysia. Heap after collection was about 10, 17, and 17 MiB respectively. The fixtures
bundle Nifra and load the peer packages directly, so this is the process footprint of those
deployment shapes, not a packaging-neutral comparison of framework memory.

None of these snapshots establishes a leak or long-term memory growth. Sampled allocation bytes
exclude some native allocations and cannot be substituted for RSS, external memory, or retained
heap. Bun/JSC and Deno allocation behavior cannot be inferred from Node/V8's heap sample.

## Optimization priorities

1. Reduce POST promise/continuation allocations between Node body collection, bounded JSON parsing,
   validation, and handler delivery. Preserve delivered-byte limits, prototype-poisoning defenses,
   abort handling, and error semantics. The measurable target is roughly 1.1 KiB/request in the
   small real-world POST, followed by a CPU and end-to-end A/B against Fastify.
2. Reduce generic GET routing/parameter/query materialization and synchronous lifecycle dispatch.
   Allocation volume is already competitive, so avoiding unnecessary checks and function dispatch
   is a stronger hypothesis than object pooling. Target Bun and Node independently.
3. Validate any change across short, long, encoded, repeated-key, and hostile query shapes, plus
   both synchronous and asynchronous lifecycle semantics. A microbenchmark win alone is insufficient.

A trial replacing the query parser's character scan with two native `indexOf` searches improved
long plain queries, but the encoded-query Bun sample regressed by 38%. It was rejected and the
temporary candidate removed. No framework runtime optimization is retained from this investigation.

For a consistency claim, repeat on quiet Linux hardware with fresh processes, randomized balanced
order, complete success counts, per-round ratios, and confidence intervals. Keep generic and
closed-shape results separate. The existing Linux rig can remove macOS loopback compression, but
its VM still shares host load and thermals.
